# Performance Contract

## Principle

Performance is a product requirement and an architectural constraint. The template must not rely on a later optimization plugin to undo avoidable bloat created by the foundation itself.

## Field targets

The project aligns with current Core Web Vitals guidance for good user experience:

- LCP < 2.5 s
- INP < 200 ms
- CLS < 0.1

Reference: https://developers.google.com/search/docs/appearance/core-web-vitals

These are field-oriented targets. CI lab budgets are proxies and must catch regressions without pretending to guarantee field results.

## Frontend defaults

- No jQuery dependency from project-owned frontend code.
- No third-party font requests by default.
- Prefer system/local fonts.
- No global JavaScript bundle when a feature can be implemented with HTML/CSS.
- JavaScript modules load only on pages/components that require them.
- Prefer `theme.json` for standard styling and WordPress block stylesheets for larger block-specific CSS.
- Avoid loading a monolithic stylesheet for blocks not used on a page.
- Images include intrinsic dimensions when known.
- Below-the-fold images use native lazy loading when appropriate.
- Hero/LCP media must not be accidentally lazy-loaded.
- Responsive images use WordPress image APIs and `srcset`/`sizes`.
- SVG is preferred for project-owned simple icons/marks where safe and appropriate.
- Animations respect `prefers-reduced-motion`.

WordPress references:
- https://developer.wordpress.org/themes/global-settings-and-styles/introduction-to-theme-json/
- https://developer.wordpress.org/themes/features/block-stylesheets/

## Asset policy

Every asset must answer three questions:

1. Is it necessary for the current page?
2. Can WordPress/browser primitives solve it without another dependency?
3. Can it load later without harming the critical experience?

New third-party frontend dependencies require a documented justification and measurable before/after evidence.

## Image policy

The foundation must:

- preserve WordPress responsive image generation;
- support modern formats supplied/generated by WordPress/hosting tooling without hard-coding one provider;
- avoid CSS background images for meaningful editorial content when an `<img>`/`picture` is more semantic;
- define width/height or aspect ratio to reduce layout shifts;
- expose a predictable hook for high-priority LCP media;
- avoid duplicate preload/fetchpriority hints.

## Fonts

Default preset fonts should be system-stack or locally bundled with explicit licensing. Remote Google Fonts or similar services are opt-in project decisions, not defaults.

When local fonts are used:

- use only required weights/styles;
- prefer WOFF2;
- define appropriate `font-display`;
- preload only the critical face(s) proven to help;
- do not preload every font file.

## Caching compatibility

The Core must remain compatible with common page/object/cache layers and CDNs. It should not assume a specific Hostinger, LiteSpeed, Cloudflare or Redis setup.

Dynamic endpoints such as Markdown/llms output must define deterministic cache behavior and invalidation on relevant content changes.

## Database/query discipline

- No unbounded frontend queries.
- Avoid per-item query loops where one query can fetch the relationship set.
- Cache derived global entity configuration when safe.
- Do not execute expensive GEO/Schema analysis on every request if it can be resolved from persisted/normalized metadata.
- Admin diagnostics must be explicit actions, not hidden work on every page load.

## Performance budgets

Phase 2D locks the initial numeric CI budgets from representative real WordPress fixture evidence rather than guessed thresholds.

The authoritative machine-readable contract is `tests/performance/budgets.json`. The current base fixture enforces, for both EN and ES:

- Lighthouse performance score >= 95;
- lab LCP <= 1,200 ms;
- lab CLS <= 0.05;
- Total Blocking Time <= 100 ms;
- total transfer <= 26,624 B;
- HTML transfer <= 14,336 B;
- external CSS transfer <= 4,096 B;
- total JavaScript transfer <= 8,192 B;
- requests <= 7;
- DOM nodes <= 112;
- third-party requests = 0;
- project-owned frontend JavaScript = 0 B.

These budgets are regression controls for the current foundation fixture. They are not universal budgets for every future preset or content-heavy page. A scoped feature/preset may need its own measured contract, but it must not silently weaken the base fixture.

The measured baseline, rationale, runner evidence and limitations are recorded in `docs/PERFORMANCE_BASELINE.md`.

## Measurement strategy

CI/lab:
- Lighthouse 13.4.1 on representative EN/ES WordPress fixtures;
- three samples per language with median aggregation;
- transfer sizes by resource type;
- total requests, third-party requests and project-owned JS;
- DOM size;
- clean WordPress runtime diagnostics;
- raw Lighthouse JSON preserved as CI evidence.

Production:
- Search Console Core Web Vitals and/or RUM when a deployment enables it;
- compare field data against lab assumptions;
- log material performance regressions in `docs/engineering/ERRORS_AND_SOLUTIONS.md`.

## Budget-change rule

A failing budget is not fixed by raising a number without evidence. A deliberate budget change requires:

- before/after measurement;
- the reason the extra cost is necessary;
- the user/product benefit;
- validation that the broader field targets remain realistic;
- updated documentation and regression coverage.

## Acceptance

A customer-facing feature is not complete when it visually works but introduces an unexplained critical-request dependency, layout shift, excessive global asset or measurable regression outside the agreed budget.
